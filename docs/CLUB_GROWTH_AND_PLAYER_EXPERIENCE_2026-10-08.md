# 선수 얼굴·승격 구단 이미지·실제 조작 검증

## 이번 변경의 목적

선수 얼굴을 더 다양하게 만들고, 5부 동네 구장에서 1부 경기장까지 구단의
귀환이 그림에 드러나도록 했다. 홈에서는 현재 리그·순위·승점·자금·가용 선수·
다음 상대와 네 핵심 행동을 먼저 읽는다. 킥오프 전에는 우리/상대 선발의 계산
종합 능력과 체력·출전 가능 인원을, 경기 중에는 점유율 추정·슈팅·체력·교체를
같은 네 칸에 보여준다. 준비 단계의 선발 버튼과 팝업도 ‘선발 · 후보’로 표시한다.
상대 보고서는 준비 화면의 ‘상대 정보’로 바로 연다. 팝업을 닫아도 자동 재개하지 않는다.

## 구단 성장의 표현과 실제 규칙

- 현재 리그에 맞는 다섯 경기장 그림과 5→4→3→2→1 단계 표시를 홈에 연결했다.
  단계 표시는 현재 위치이며, 이전 승격 횟수나 달성 기록을 만들어내지 않는다.
- 확정 시즌 결산은 이번/당시 경기장과 확정 다음 리그 경기장을 비교한다.
  승격·강등 모두 실제 `division`/`nextDivision`을 따른다. 진행 중 시즌은 현재
  순위만으로 다음 리그 그림을 보여주지 않는다. 그림을 읽는다고 시즌을 넘기지 않는다.
- 1부 훈련·유소년 화면에는 훈련 캠퍼스 그림이 보인다. 모든 그림은 구단 규모
  일러스트이며, 실제 관중·시설 수준·수용 인원·수입 또는 능력 보너스가 아니다.
- 현재 schema/engine 10과 38/46경기, 유효한 저장·선수 신원·계약·RNG·기록을 유지한다.

## 얼굴과 생성 출처

내장 `image_gen.imagegen`의 **새 이미지 생성 모드**를 사용했다. 참조 사진이나
게임 화면을 생성 입력으로 제공하지 않았고, 타 게임 자산을 복사하지 않았다.
생성 결과는 직접 보고 확인했으며 Pillow는 RGB WebP 형식 인코딩에만 사용했다.
얼굴을 그리거나 변형하는 Python 이미지 편집은 하지 않았다.

| 자산 | 결과 | 최종 파일 |
|---|---|---|
| 추가 선수 얼굴 | 1254×1254, 8×8의 성인 남자 축구 선수 64명 | `source/dist/assets/player-faces-v18.webp`, 190,436바이트 |
| 구단 성장 | 2048×768, 3×2의 16:9 그림 6개 | `source/dist/assets/club-growth-v1.webp`, 342,258바이트 |

얼굴 총 156셀(기본 28 + 확장 64 + 추가 64)을 공유한다. 손헝민의 21번 셀을
포함한 기본 선수·초기 영입 선수의 대응은 유지한다. 생성/상대 선수는 신원
해시로 확장 128셀을 사용하며, 한 구단 상대 선발 11명은 서로 다른 셀이다.
확장 풀이 커지므로 일부 이전 생성 선수의 **표시 얼굴**은 달라질 수 있지만
저장된 이름·신원·능력·계약은 바꾸지 않는다. 경기장의 작은 피부색도 해당 셀을
읽고, 얼굴 이미지는 명단/상세에만 표시한다. 경기 공 앞을 큰 얼굴로 가리지 않는다.
이미지는 원본 일러스트이며 라이선스된 실제 선수 사진이 아니다.

최종 생성 프롬프트는 [선수 얼굴](PLAYER_PORTRAITS_V18_PROMPT.txt)과
[구단 성장](CLUB_GROWTH_V1_PROMPT.txt)에 그대로 저장했다.

## 참고한 정보 배치

[FM26 Mobile 공식 소개](https://www.footballmanager.com/fm26/features/football-manager-26-mobile-new-features-showcase)의
[공식 전술 화면](https://cdn.footballmanager.com/site/inline-images/ARS_TACTICS_IFB_16PRO_ENG_opt.jpg)은
배치판과 선발/포지션 목록을 함께 두고, 관련 결정은 별도 메뉴로 둔다.
[공식 2D 경기 화면](https://cdn.footballmanager.com/site/inline-images/NEW_MCI_GOAL_2D_16PRO_ENG_opt.jpg)은
점수·시간·필드·중계를 중심으로 구성한다. 이 두 이미지를 브라우저에서 직접
확인했으며 저장소에는 복제하지 않았다. 이전 작업에서 확인한
[EA FC Mobile 게임 플랜 공식 자료](https://www.ea.com/games/ea-sports-fc/fc-mobile/news/fcm27-game-plans-deep-dive)도
결정 정보를 경기 준비와 경기 중 단계에 나눠 두는 설계의 참고 자료다.
우리 앱은 세로 폰의 공간과 44px 조작을 우선해 상세 목록은 내부 스크롤로 유지한다.

## 실제 버튼으로 플레이한 결과

별도 QA Chrome의 390×844 터치 컨텍스트에서 아래를 수행했다. 상태 강제 설정을
사용한 레이아웃/승격 픽스처와, 실제 사용자 조작 플레이를 구분했다.

1. 처음 시작→두 서사 페이지→우리 팀 전체 18명→손헝민 상세→명단으로 돌아가기.
2. 전술 안내→경기 전 선수 대화→킥오프 준비→상대 정보→선발·후보 확인.
3. 실제 속도 설정→킥오프→진행 중 전술 창으로 일시 정지→수동 재개.
4. 45분 하프타임에서 나갈 선발과 후보를 직접 눌러 교체→후반→90분.
5. 경기 결과 팝업→결과 확정→다음 라운드 홈→페이지 재접속→구단 이어하기.

총 경기 관전 구간은 107,278ms, 1:0/슈팅 3:2였다. 같은 초기 상태와 하프타임
교체를 독립 엔진에서 실행한 전체 경기 상태가 정확히 일치했다. 대화·교체 이후
난수·결과를 화면 연출이 바꾸지 않았다. 멈춘 팝업은 시간/상태를 유지하고,
닫은 뒤 수동 재개한다. 결과 확정 이후 구단은 재접속에도 정확히 복원됐다.
브라우저 페이지 오류는 없었다. 이는 물리 휴대폰에서 직접 플레이한 결과는 아니다.

## 실제로 발견해서 고친 불편

- 경기 시작 전의 ‘선수 교체’ 표현을 선발 준비 표현으로 바꿨다.
- 상대 보고서를 다른 창의 메뉴에서 찾던 경로를 준비 화면 한 번 탭으로 줄였다.
- 320×568 홈의 마지막 버튼 일부가 하단 메뉴 뒤에 가려졌다. 해당 작은 화면에서
  그림 폭만 줄여 16:9 원본 셀 비율과 버튼 44px를 유지했다.
- 640×360/844×390 가로 홈의 그림이 화면을 차지해 결정을 읽기 어려웠다.
  경기장과 핵심 정보/네 행동을 좌우에 두고 하단 메뉴를 44px 조작으로 유지했다.

## 크기·저장·회귀 검증

320×568, 360×640, 390×844, 412×732, 640×360, 844×390,
768×1024, 1440×900에서 준비/전반/하프타임/후반/65분/마지막 구간/종료의
일곱 경기 단계를 확인했다. 가로 넘침이나 경기 페이지 스크롤이 없고, 핵심
버튼은 44px 이상이며 중계는 15px(짧은 가로 14px)다. 작은 320 화면의 필드는
178px, 가로 640 필드는 149px다. 상세 선수/상대/기록 목록은 내부 스크롤한다.
홈 핵심 카드 하단/메뉴 시작은 320×568에서 499/503px, 360×640에서 542/575px,
640×360에서 297/307px, 844×390에서 330/336px로 겹치지 않는다.
모든 기사 본문과 모든 선수 상세를 동시에 첫 화면에 넣었다는 뜻은 아니다.

46라운드를 마친 유효한 5부 2위 테스트 구단에서 결산 열기는 전체 구단을 바꾸지
않았다. 확인된 5→4부 그림 비교를 보고 명시적으로 다음 시즌 시작을 누른 뒤에만
4부 홈 그림이 보였다. 그 상태도 재접속에서 복원됐다. 합성 저장/스크린샷/QA
스크립트는 `work/`에만 두고 커밋하지 않는다.

- 전체: **104 suites / 795 checks**.
- 공개 PWA: **14그룹**, 모듈형 캐시의 새 두 이미지와 완전한 인라인 공개 셸 검증.
- Android 자산/브리지: **11그룹**. 원격 native 계측은 기존 6개 테스트에
  새 얼굴/성장 아틀라스 실제 디코드와 준비 HUD·한 번 탭 상대 진입 검사를 포함한다.
- 공개 HTML: **3,328,344바이트**.
- Android HTML: **3,329,973바이트**, SHA256
  `ecd09d7402de54b4eb95db790db8060e122d220599ba6af3e855c0a3fdb68894`.

## 성능 측정과 제한

한 PC의 Chrome 360×640 터치 컨텍스트에서 CPU를 4배 제한하고, 이전 b7ac43f와
이번 번들을 양쪽 순서로 각각 세 번 로드했다. 매번 별도 컨텍스트를 만들고,
실제 속도 버튼/킥오프를 눌러 각 번들의 경기 12초도 측정했다. 테스트 실행이나
다른 QA 브라우저를 동시에 돌리지 않았다. 단일 PC 측정이며 기기별 보장은 아니다.

| 지표 | 이전 번들 | 이번 번들 |
|---|---|---|
| HTML 크기 | 2,607,362바이트 | 3,328,344바이트 (+27.65%) |
| 로드 6회 범위 | 797.0–2198.6ms | 886.4–1946.2ms |
| 실제 홈 버튼→홈 준비 6회 | 908–2832ms | 1061–1860ms |
| 아틀라스 전체 디코드 6회 | 96.3–233.1ms | 158.8–220.3ms |
| 경기 프레임 간격 중앙값, 2회 | 16.7/16.7ms | 16.7/16.7ms |
| 경기 프레임 간격 p95, 2회 | 66.6/16.8ms | 16.8/16.8ms |
| 12초당 long task, 2회 | 53/5개 | 7/3개 |
| 해당 long task 최댓값, 2회 | 141/96ms | 64/80ms |

측정 순서와 브라우저/머신 예열에 따른 편차가 커서 이번 변경으로 로딩이
빨라졌다고 주장하지 않는다. 그림 추가는 디코드/첫 전송 부담을 늘린다.
WebP 2파일을 공유 규칙으로 한 번씩 넣고, 카드마다 base64를 복제하지 않는다.
성장 그림은 홈/결산에만 그리며 숨긴 홈은 경기 중 다시 계산하지 않는다.
준비 전력 계산도 킥오프 전 표시 단계에만 한다. 기존 제목 준비 게이지와
Android 로더·자동 저장/오프라인 캐시는 유지한다. 실제 저사양 휴대폰에서
장시간 플레이의 발열·메모리·프레임은 별도 확인이 필요하다.

APK/AAB·lint·Android 에뮬레이터의 **최종 원격 결과와 해당 커밋의 다운로드**는
[PR #24](https://github.com/jaeseok614/win-again-football/pull/24)의 최신 검증 기록에서
확인한다. 예전 빌드 결과를 이번 코드의 검증으로 간주하지 않는다. APK는 테스트
설치용이고 미서명 AAB는 직접 휴대폰 설치 파일이 아니다. 새 CI의 debug 서명이
이전 설치와 다를 수 있으므로 설치/제거 전에 게임 저장 파일을 내보낸다.
이번 작업은 Play 공개 게시나 출시 서명 완료를 뜻하지 않는다.
